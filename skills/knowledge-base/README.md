# Knowledge Base

A personal knowledge management pipeline for documents: drop files into an inbox, get renamed, summarized, indexed, and organized output.

## Problem

Research and reading accumulate faster than they can be organized. PDFs land in Downloads. Interesting articles get bookmarked and forgotten. When you need to find what you read about a topic six months ago, there is no reliable way to search it.

The standard workaround is a folder with vague names and files you cannot find. The other workaround is a note-taking app that captures fragments but not full documents. Neither gives you a searchable, citable record of what you have actually read.

## Approach

The knowledge base treats documents as first-class citizens. Each document gets:

1. **A citation-standard filename** (`YYYY-MM-DD LastName. Title.ext`) so files sort chronologically and are identifiable without opening them.
2. **A structured summary** (`_summary.md`) generated by a summary skill appropriate to the document type (academic or general). The summary opens with a frontmatter block that records the citation, the reading depth, the reading model, and how complete the captured source was. The summary is the primary reference artifact.
3. **A full-text extraction** (`_text.md`) for PDFs, enabling downstream search and slide generation without re-reading the source.
4. **A generated index row** in `index.md`, rendered from that frontmatter by script. Nothing in `index.md` is hand-written, and no mode reads the file whole; membership checks are a `grep`, and full-text questions go to the search index.

Documents are organized into topic folders you define. The skill does not impose a taxonomy; it discovers whatever folders exist and suggests assignments based on content.

## Structure

`SKILL.md` is the substrate: locations, storage patterns, the frontmatter contract, the index format, the helper commands, and a dispatch table. Each mode's procedure lives in its own file, and a run reads the substrate plus exactly one mode file:

| File | Mode |
|---|---|
| `references/inbox.md` | Process Inbox |
| `references/qa.md` | Q&A |
| `references/move.md` | Move Project |
| `references/slides.md` | Slides |
| `references/slides-headless.md` | Slides, unattended overrides |

Search and Status are short enough to stay inline in `SKILL.md`.

## Operating Modes

**Process Inbox (`/kb`)**
Scan the inbox folder for new files. Each item is processed in its own subagent for context isolation. The parent reads the appropriate summary skill format before launching agents, then inlines those instructions into each agent prompt. After processing, each item is filed into its best-fit topic folder immediately and a report shows where everything landed; you redirect after the fact ("move X to Y") rather than approving each move in advance. Items with no clear fit go to your overflow folder, flagged; likely duplicates are held in the inbox for a decision.

Supports three processing levels:
- Full: all pages, produces `_text.md` and `_summary.md`
- Triage: pages 1-4 only, produces `_summary.md`
- Lite: uses a companion `.txt` file you provide, produces `_summary.md` without reading the PDF

URL items are captured by a script rather than written by the model, and the script's exit code sets the provenance field mechanically. A capture that came back incomplete is marked `partial`; an item rebuilt from web-search excerpts because nothing could be captured is marked `excerpts`. Writing a source's body yourself after a failed fetch is prohibited outright.

**Q&A (`/kb ask [question]`)**
Answers questions grounded in indexed sources. Narrows by topic, searches, greps the index, selects the 5-15 most relevant documents, reads their summaries, and synthesizes a cited answer. Distinguishes between what sources say, inference, gaps, and contradictions, and flags any source whose capture was incomplete rather than citing it as the publication. Optionally saves the answer as a notes artifact, which is deliberately not indexed.

**Move Project (`kb move <source_dir> <topic>`)**
Files the output of a content skill (slides, summary, and so on) that ran outside the knowledge base. Inventories artifacts, renames them to citation convention, runs a duplicate check on the renamed stem, moves everything into a per-document subfolder, and refreshes the index, recents, and search.

**Search (`kb search <query>`)**
Keyword search over the full body of every summary and text extraction, for the "find me everything that touches X" question rather than "answer this." Returns ranked hits with snippets and file paths, and does not synthesize. This mode assumes a full-text index (the reference implementation is a SQLite FTS5 database; any equivalent works, and `grep -r` is the fallback). The full-text index is treated as a fast accelerator over the authoritative `index.md`, never as the source of truth for what the knowledge base contains.

**Slides (`kb slides <target>`)**
Build a slide deck from a knowledge base item, an inbox item, a file path, or a URL in one step, and keep the knowledge base correct on both sides of the build. The mode selects a generator and a tier, then takes one of two directions:

- **Already filed:** it reads the item's frontmatter and applies a reuse bar (a full deep read by a strong model). At the bar, the filed text and summary are reused and nothing is re-read. Below the bar, the item is re-ingested in place first, with the old artifacts preserved as timestamped copies, so the deck is never built on a thin record.
- **New to the knowledge base, default deep tier:** nothing is filed first. The deck generator reads the source once and writes the text, the summary, and its own source brief in that single pass, and the workflow files the finished set afterwards. This removes a read that used to happen twice.

The Beamer route and any URL target keep the file-first order, and the lite tier has always filed after. Before any handoff, the mode reads the source's provenance field and asks in plain language if the filed source is incomplete; a yes is passed to the generator as a token, so nobody has to remember one.

**Status (`kb status`)**
One-screen health readout: index-versus-full-text row drift, index freshness and integrity, inbox backlog counts, and a warning when any topic folder grows past a size threshold. Read-only; no content reads and no disk walk, so it is cheap enough to run before deciding whether a maintenance pass is needed.

## Design Rationale

**Agent-per-item architecture.** Each inbox item runs in its own subagent. This prevents content and image accumulation from hitting API request size limits on large batches. It also forces the parent to read and inline the correct summary format before launch, preventing improvised summaries that drift from the knowledge base's format standards over time.

**Citation-first naming.** The `YYYY-MM-DD Last. Title.ext` convention is borrowed from academic reference managers. Files sort by date, identify by author, and remain readable in a file browser without any app. The naming convention is the most durable part of the system.

**The index is generated, not maintained.** `index.md` is rendered from every summary's frontmatter by a script, atomically and guarded by a count floor. Nothing is appended by hand, so a row cannot drift from the document it describes, and a document appears the moment its summary carries a frontmatter block. To change a row, edit the frontmatter and regenerate. Because the index is never read whole, it can grow past what fits in a context window without breaking any mode.

**One storage pattern, with the old one still readable.** Pattern A, a per-document subfolder holding the source and every artifact, is the default for all new filing. Pattern B, flat files side by side in the topic folder, is legacy: nothing produces it any more, but every reader still handles it, and a slides run promotes a flat item to Pattern A when it touches one.

**Provenance is mechanical, not remembered.** How complete the captured source was is recorded in the summary's frontmatter by the fetch script's exit code, not by anyone's judgment at the end of a long run. Downstream slide skills read that field and gate on it, so a paywall preview or a web-search reconstruction cannot quietly become a deck presented as the publication.

**A figure annotation carries the printed caption, never a value read off the plot.** Text extraction transcribes what is printed. A table's cells are printed characters and transcribe normally; a plotted value is not, and recovering one means measuring a pixel against an axis. This is stated as a prohibition rather than a preference because it is the rule that has actually put wrong numbers on delivered slides, and because a later checking pass proved no better at reading the same plot.

**Blog posts as first-class knowledge.** Your own writing is filed into topic folders alongside external sources, tagged `[blog]` in the index. This makes it possible to ask the knowledge base "what have I written about X" alongside "what have I read about X."

**Topic folders are dynamic.** No hardcoded taxonomy. Any subdirectory (except reserved names like `aa-inbox/`, `aa-blog/`, `aa-recents/`) is a topic folder. Create a new folder and the next inbox run discovers it automatically.

## Usage

1. **Set up your knowledge base root.** Create a directory (for example, `~/knowledge-base/`) with an `aa-inbox/` subfolder inside it. Update the path in `SKILL.md` to match.

2. **Wire the helper commands.** `SKILL.md` has a Helper commands table naming the small scripts the skill calls: index generation, full-text search and reindex, duplicate check, status, recents rebuild, and URL capture. Each entry states its contract, including the exit codes the URL capture must return. Every place that calls one also names its fallback, so you can start with `grep -r` and add scripts later.

3. **Configure your summary skills.** This skill calls out to an academic summary skill and a general summary skill. Adapt the references in `SKILL.md` and `references/inbox.md` to point to whichever summary skills you use. The format template from those skills is inlined into agent prompts at runtime.

4. **Drop files into `aa-inbox/`.** Any supported file type: PDF, markdown, DOCX, RTF, TXT, HTML, PNG, JPG, or a `.urls` file containing URLs to fetch. A `urls.txt` in that folder is a persistent drop target: processed lines are cleared, unusable lines are parked as comments.

5. **Run `/kb`.** The skill scans the inbox, processes each item in its own agent, files each into its best-fit topic folder, and reports what landed where. Redirect anything misfiled with "move X to Y."

6. **Ask questions with `/kb ask [question]`.** The skill narrows by topic, searches, reads the relevant summaries, and synthesizes a cited answer.

7. **File pipeline output with `kb move`.** When a slides or summary skill runs on a document outside the knowledge base, use `kb move` to file the artifacts into the appropriate topic folder.

8. **Find things with `kb search <query>`.** For "what do I have that touches X," run a keyword search over the body of every summary and extraction. Filters for date, type, and topic folder are available where you maintain a real index.

9. **Build slides with `kb slides <target>`.** Point it at a knowledge base item, an inbox file, a path, or a URL. Add `beamer` for the Beamer route via [slides-content](../slides-content/) and [beamer](../beamer/), or `lite` for the cheap tier. Add `headless` for an unattended run with every decision auto-resolved.

10. **Check health with `kb status`.** Cheap enough to run any time; it tells you whether the index and the search database still agree and what is backed up in the inbox.

## Output

For each processed document, filed into `<topic>/<stem>/`:
- `YYYY-MM-DD Last. Title.ext` (renamed source file)
- `YYYY-MM-DD Last. Title_text.md` (full-text extraction, PDFs only)
- `YYYY-MM-DD Last. Title_summary.md` (structured summary, opening with the frontmatter block)
- One generated row in `index.md`
- A symlink in `aa-recents/`, which holds the most recently processed items ranked by their `ingested:` date

Slide builds add `_slides.pptx` (or `_slides.pdf` on the Beamer route), a review render, and a `_build/` folder, all filed into the same per-document subfolder.

The index row format:
```
| Date | Author | Title | Topic | Summary |
| 2026-03-18 | Ipeirotis | Scalable Oral Assessments Using Voice AI | AI-articles | Voice AI oral exams at $0.42/student with multi-model deliberation achieving alpha=0.86 |
```

The Summary cell is the `index_line` field from the document's own frontmatter: one sentence that locates and disambiguates the document rather than summarizing it. To change a row, edit that field and regenerate.

## Installation

1. Copy this folder into `~/.claude/skills/knowledge-base/`, keeping `SKILL.md` and the `references/` subfolder together. A mode file that is missing means that mode has no procedure.
2. Open `SKILL.md` and update the knowledge base root path (the `~/knowledge-base/` line near the top) to match where you want your knowledge base to live. Adjust the reserved-folder names (`aa-inbox/`, `aa-blog/`, `aa-recents/`) if you use different conventions.
3. Wire the helper commands in the Helper commands table, or start with the named fallbacks and add them as you go.
4. Adapt the references to summary skills (in `references/inbox.md` and the Integration section of `SKILL.md`) to point at whichever summary skills you have installed, or adapt them to use your own summary format.
5. Confirm Python 3 is on your `PATH` (used for PDF text extraction).
6. (Optional) Install the companion [knowledge-base-update](../knowledge-base-update/) skill for periodic index sync and health checks.
7. Restart Claude Code (or run `/skills` to reload).
8. Trigger by saying "kb," "process inbox," "kb ask <question>," or any other phrase listed under Usage.
